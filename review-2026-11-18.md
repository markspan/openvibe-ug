# Review of the UG fork against upstream (4891073)

**Second pass, at commit 7c6afdc (18 November 2026).** All of the fork's code was read again: 338 files, about
35,750 lines added and 4,400 removed. About 16,700 changed lines are code, in 243 files; the rest is scenario XML,
documentation and test input, checked only where code depends on them. This pass re-read the code written for the first
pass's fixes (UG.md 2.41 and 2.42), read in full the areas the first pass had only skimmed (the LSL Output writer, the
display's ring buffer, the XDF writer and LSL recorder, the P300 speller's port, the display QML, the Python scripts,
the build files), and checked the documentation against the code.

The first pass, at commit 8551865, is summarised at the end, with what became of each finding.

## In short

The fork is in good shape. The first pass's high findings are fixed and the fixes hold up: one copy of the montage code
(`CharmeleonDriver`), no Charmeleon in the generic driver interface, a build that compiles outside Windows again, one
display panel and trace view, an explicit channel localisation link, an exclusive port bind and backslash-proof paths.

What remains is smaller. One lifetime hazard in the P300 speller's view could crash Designer when a scenario stops.
Three pieces of documentation lag behind the code. Today's new logic has no tests of its own yet. And there is a handful
of small items, one of them a real (harmless) bug.

## 1. Medium

### 1.1 The P300 view keeps a raw pointer to its QML item

`CP300SpellerView` holds its item as `QQuickItem* m_visualItem`. `show()` runs on the player thread: it tests the
pointer and passes it to `QMetaObject::invokeMethod` as the call's context, and the destructor calls `deleteLater()` on
it. But once the window manager reparents the item, QML owns it and may destroy it first; the Signal display's
controller says exactly this, and holds its item in a `QPointer` for that reason. The lambda in `show()` already
captures a `QPointer`; the two outer uses do not. A dangling pointer there can crash Designer when a scenario stops.

**Fix:** hold the item in a `QPointer` and test it where it is used.

### 1.2 Documentation behind the code

- **The Acquisition client's box page** (`extras/plugins/processing/acquisition/doc/Doc_BoxAlgorithm_AcquisitionClient.dox-part`)
  still has upstream's four-output layout: Outputs 1 to 3 empty, "Channel localisation flow" under Output 4, and a
  description that speaks of experiment information. The box now has Signal, Stimulations and Channel localisation as
  outputs 1 to 3. The page should say so, and what the localisation output carries (one row per placed channel, x, y, z).
- **`speller.md`**, in its table of the legacy and the current client box, lists the current box's outputs as "Signal,
  stimulations"; it now has Channel localisation too.
- **OpenViBE contradicts itself on the localisation frame.** `documentation/Stream Structures/Stream Structures.md`
  (2008) says X right, Y front, Z up. The electrode files OpenViBE ships (`electrode_set_standard_cartesian.txt`: Fpz at
  +x, T7 at +y, Cz at +z) and the advanced visualisation that reads them (`CBoxAlgorithmViz`) use x to the nose, y to the
  left ear, z up. The fork follows the files, which is right in practice, but `ovChannelInfo.h` names only the file. It
  should name the conflicting description, so that a reader of `Stream Structures.md` is not misled.

### 1.3 Today's shared logic has no tests of its own

- **`CharmeleonDriver`**, the channel-list logic both amplifier drivers now share (fitting the names to the amplifier,
  recording only named channels and restoring the list, the hints, a montage set or cleared), is only tested through
  `CharmeleonMontage`'s tests and on hardware. It needs no amplifier: a small fake driver with a fixed channel list would
  test all of it, as `CharmeleonMontageTest` does for the rules.
- **The localisation path end to end:** the BrainVision writer's test scenario (`BrainVision-UG-Write-test.xml`) has
  nothing on the writer's new third input, so `[Coordinates]` is never written in a test. Upstream's *Electrode
  localisation file reader* box, reading `electrode_set_standard_cartesian.txt`, could feed it, and `check_brainvision.py`
  already checks the section when it is there.
- **`quoteArgument()`** in `Charmeleon.cpp` (Windows command-line quoting) is a pure function without a test; its rules
  are easy to get wrong.

## 2. Low

### 2.1 The LSL recorder reopens a stream it can not record

In `CLSLRecorder::run()`, a stream whose sample format can not be recorded reaches `continue` before it is stored. The
next pass, a second later, opens a new inlet to it and prints "has a sample format that can not be recorded" again, for as
long as it stays selected. Harmless, but a log full of the same line. **Fix:** remember the stream as skipped.

### 2.2 A remote START runs a driver's `init()` on the control thread

`Acquisition::start()`, and with it the driver's `init()`, runs on whichever thread calls it: the UI thread for Play, the
control API's thread for a remote `START_ACQ` (`CNetAcqControlAPI::CmdStartAcquisition`). The fork's drivers change the
channel list, the note and the locks in `init()`, which the UI reads, and `CharmeleonDriver`'s own state is not guarded.
Designer's client box never sends `START_ACQ` (it only asks for the stream), so only another program could start it this
way. Upstream's design, which the fork's drivers lean on more; worth a line in `AbstractDriver.h`, or a hand-off to the UI
thread.

### 2.3 The Qt location is set in two places

`pixi.toml` sets `Qt6_DIR` to `C:\Qt\6.9.3\...` on activation, while its own comment, the build instructions and this PC
use `CMAKE_PREFIX_PATH` (here `D:\Qt\...`). The workflow's comment says its `QT_VERSION` "must match Qt6_DIR in
pixi.toml". One way, documented once, would do. (`pixi.toml` also lets CMake and Ninja be any version; `pixi.lock`
still pins them.)

### 2.4 Smaller items

- **The server clock is written out three times:** `AbstractDriver::timestamp()`, `Acquisition::immediateTimestamp()`
  (upstream) and the LSL Output writer's `serverClockSeconds()` (fork), whose comment says "the same clock as
  `AbstractDriver::timestamp()`". One shared function keeps them from drifting apart.
- **`XDFWriter::footerXml()`** writes numbers through an `ostringstream` not set to the classic locale, as
  `ovChannelInfo.h` is. A process-wide C++ locale with a decimal comma would corrupt the footer.
- **`CBoxAlgorithmChannelSelector.cpp`:** `DescribeChannels()` and `DescribeMatching()` have external linkage at global
  scope; an anonymous namespace keeps them to the file.
- **`MultiSelectParameter.qml`** defines `OutlineButton` and `OutlineCheckBox` inline. They are design-system controls
  (`OVDesignSystem`); another control would have to copy them.
- **The LSL Output writer** owns its outlets with raw `new`/`delete` (upstream's style); `std::unique_ptr` would do.
- **`CharmeleonDriver::channelInfo()`** reads the montage file again at Play rather than reusing what `init()` just
  applied. One extra file read; harmless.
- **The display's ring buffer** draws a gap in an LSL stream as each channel's last value, so a gap does not show as one.
  A choice, not a fault; a marker or a break in the line would show lost data.

## 3. Accepted

These first-pass findings were looked at and left as they are, by choice:

- **The drift is still computed** in a thread of its own on every acquisition, and shown nowhere.
- **The BrainVision writer (UG) is largely a copy** of upstream's Gipsa writer, kept so that upstream's box stays
  unchanged.
- **The courteous error messages repeat** the same sentences at several call sites.
- With their reasons in UG.md 2.42: Designer's player loop wakes every millisecond; `CharmeleonMontage` words its
  summaries in English; Designer's console goes to a log file; the stimulations stay about 100 ms behind the signal.

Upstream's, not addressed: the top-level install copies Qt's whole `bin` folder, Qt's tools and debug DLLs among them,
and Qt's own `designer.exe` next to OpenViBE's.

## 4. What holds up

- **The first pass's fixes** read as intended: `CharmeleonDriver` has one apply path and three small hooks; the
  Charmeleon watcher and closing are platform-neutral and wait on the processes; the localisation output is sent once,
  with the signal's header, and read before the signal; `CDisplayPanel`, `TracePanel.qml` and
  `CSignalTraceItem::refresh()` do what the two copies did, and the page rule is tested.
- **The LSL code:** the reader and recorder hand data over under one mutex each, follow LabRecorder's file layout, and
  were checked against pyxdf and MATLAB. The ring buffer's time locking and resynchronisation are sound.
- **The P300 speller's port** sends each stimulus when the frame that shows it is on screen, or after a second without
  a frame, in order and with monotonic times; its state is split out and tested.
- **The Python stimulation helper** keeps its queues in date order and sends future-dated stimulations on time.
- **Pure cores with tests:** `BlockStamps.h`, `SteadyTrigger.h`, `SampleBlocks.h`, `StimulationDelay.h`,
  `CharmeleonMontage`, `ovChannelInfo.h` (now with the frame conversion both ways), `SignalScaling.h` (now with the page
  rule), `TraceShading.h`, `P300SpellerState`.
- **Documentation:** UG.md lists every change with its files, behaviour and consequences; the tagging rule now also
  covers the ported files; no stale references to removed functions, tokens or settings remain outside UG.md's history.
